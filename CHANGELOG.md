# Changelog

## 0.7.3-preview.1 — October 13, 2026

- `@assetlib/sdk-expo` supports Expo SDK 54, 55, 56 and 57. Peer ranges: `expo` `>=54 <58`, `expo-file-system` `^19.0.11 || >=55 <58`, `expo-image` `^3.0.7 || >=55 <58`, the optional `expo-video` `^3.0.11 || >=55 <58`, `react-native` `>=0.81 <0.87`; `react` stays `>=19 <20`. Before SDK 55 these packages were not numbered after the SDK; the floors are the versions Expo SDK 54.0.0 installs.
- The native file cache no longer passes `{ overwrite: true }` to `File.move` and `File.copy`. That option arrived in expo-file-system 56. On 54 and 55 those methods take one argument (expo-modules-core rejects a second) and refuse an existing destination, so saving the first release or caching the first image would have failed there. The adapter now deletes an existing destination, then moves or copies and awaits the result (a promise from 56 on). State and install ID readers already accept the `.next` journal, so a crash between the two steps loses neither. The Node test doubles now enforce one argument and no overwrite.
- Checked on October 13, 2026: `npm run verify`; the Expo source typechecked against the packages Expo 54.0.0, 54.0.37, 55.0.31 and 56.0.23 install; a new Expo SDK 54 app installed the packed core and Expo packages without peer overrides and, against the public demo workspace's release 1, drew the published images in a web export in Chrome 152, in a Release build on an iOS 27 Simulator and in a release build on an Android 16 emulator. In both native builds an in-app check replaced an existing `state.json` and cache entry through the installed adapter, and the verified cache survived a restart; on Android the app also restarted offline from the cache and drew the bundled images offline after its data was cleared. To launch with Xcode 27 the iOS build needed a UIScene delegate, which Expo SDK 54's template does not include, and pod deployment targets of at least iOS 15.1; neither concerns the SDK. A new Expo SDK 57 app (expo-file-system 57.0.7) then ran the same packed code in a Release build on an iOS 27 Simulator and a release build on an Android 16 emulator: remote images, the in-app replacement of an existing `state.json` and cache entry, the verified cache after a restart, and on Android an offline restart from the cache. Not checked: any runtime on Expo 55 or 56 (typecheck only), offline on iOS, `AssetlibVideo` clip playback on Expo 54 to 56, physical devices. `@assetlib/sdk-core` changes only its version; `@assetlib/cli` 0.4.2 and `@assetlib/audit` 0.2.1 are unchanged.

## 0.7.2-preview.1 — October 13, 2026

- `@assetlib/cli` 0.4.2, security: the GitHub workflow `assetlib init` writes (`.github/workflows/assetlib-sync.yml`) had two flaws. Its `workflow_dispatch` trigger let anyone with write access run the job that holds `ASSETLIB_TOKEN` from any branch; a first job now compares `$GITHUB_REF` with `refs/heads/main` in the shell (GitHub's own expression comparison ignores case, so `Main` would pass) and the sync job runs only after it allows the run. The app version was echoed into `$GITHUB_OUTPUT`, where a version containing a newline could add step outputs; it is now read inside the sync step into a quoted shell variable. The sync job also runs in the `assetlib-sync` environment, and the generated comment, `init`'s next steps and the CLI README say to store the token as that environment's secret with deployment branches limited to `main`, which a branch with an edited workflow cannot read (or as a repository secret in a private repository on GitHub Free, which has no environments). `init` never changes an existing workflow: apps that ran it before CLI 0.4.2 should copy the new `branch_gate` job, the sync job's `needs`, `if` and `environment` lines and its sync step, as shown in the CLI README. Node unit tests (including the gate script run under bash for `main`, `Main`, `MAIN` and other refs) and YAML parsing of the four rendered variants. The same jobs in Roam's workflow (AssetLib/demo-travel `4e9c6ba`) ran on GitHub on October 13, 2026: a push to `main` synced inside the environment with the token still a repository secret (run 38488276190), and a manual run from another branch skipped the sync job (run 38488413544).
- `@assetlib/sdk-core` and `@assetlib/sdk-expo` change only their version. `@assetlib/audit` 0.2.1 is unchanged.

## 0.7.1-preview.1 — October 13, 2026

- `@assetlib/sdk-core`, `@assetlib/sdk-expo` and `@assetlib/cli` 0.4.1 change only their version and README. No code changed.
- The core README says the catalog width and height are a reference, not a crop: they fix the aspect ratio every published image must match (the console checks it when an image is assigned and again at publish) and are the size `resolve` requests when no `pixelWidth` and `pixelHeight` are passed; published images may have any pixel size at that aspect ratio. The CLI README's adopt section says the catalog size fixes that aspect ratio and the default request, so a `@3x` source triples the default request.
- The core and Expo READMEs say state names mean nothing to Assetlib: the app chooses the state, and the console publishes a state family only when every state has an image at the placement's aspect ratio (pixel sizes may differ), so a release never mixes states from different publications.
- The CLI README says a placement someone requested in the console becomes declared by a build whose catalog has the same key, width, height, states, default state, variants and rendering; a different contract is reported as conflicting, and the console keeps its own.
- `@assetlib/audit` 0.2.1 is unchanged.

## 0.7.0-preview.1 — October 11, 2026

- `@assetlib/sdk-core`: placement membership, contract revision of October 11, 2026. The latest accepted release alone decides whether a placement has published artwork. If it has no slot with the reference's key, `resolve` returns the bundled fallback (`source: 'bundle'`, `fallbackReason: 'missing'`, the reference's `bundledAccessibility` when present) and `resolveStateSet` returns the complete bundled family. Neither reads the cache, makes a request, calls `decide` or uses an older retained release. Before, a cached image from an older release kept showing until eight newer releases had arrived, so restoring a publication that predates a placement could not take back an image a device had already downloaded for it. When the current release publishes the key, resolution is unchanged: an incompatible slot (size, rendering or state set) or bytes that cannot be downloaded or verified still fall back to compatible cached bytes from older retained releases, which are never downloaded, then to the bundled fallback. Cached bytes are kept, so publishing the same image for the key again is a cache hit. No API, type or wire format change.
- Apps that restore a publication that predates a placement now show that placement's bundled image on the first resolve after updating the SDK. An app whose current release already lacks a placement it once received may see that placement change from the old cached image to the bundled image when it updates the SDK.
- `@assetlib/sdk-expo` changes only its version, which keeps its exact core dependency in step. Its components resolve through the core, so they follow the same rule; `AssetlibVideo`'s poster is the bundled image when the placement is removed.
- Tests: the shared contract corpus adds 7 signed manifests (149 manifest cases) and `history.json` with 10 membership cases, including 4 controls that keep the history fallback for a key the current release still publishes. `test/history.test.mjs` covers state sets, animation posters, explicit arms and `decide`. Node unit tests only; no device, simulator, emulator or browser was run for this change.
- `@assetlib/cli` 0.4.0: `assetlib adopt`, and so `assetlib init`, keeps one section for coding agents between `<!-- assetlib:start -->` and `<!-- assetlib:end -->` in the app's `AGENTS.md` (created when missing), and in `CLAUDE.md` when that exists and does not import `@AGENTS.md`. It names the catalog, says to render placements with `AssetlibImage` and the generated reference, to use the placement instead of exporting art the Assetlib Figma plugin marked (a component whose description starts with "Assetlib placement"), and to add placements in the catalog with a bundled fallback, never in the console. Text outside the markers is kept; symlinks, broken markers and files over 256 KiB are left unchanged with a note. It is written only in a run that adopts something; the CLI README shows it for existing apps. Node unit tests and a scratch Expo project run of the real binary.
- `@assetlib/audit` 0.2.1 is unchanged.

## 0.6.4-preview.1 — October 11, 2026

- `@assetlib/sdk-expo`: in Safari, `AssetlibVideo` played the clip but never hid the poster, so people saw a still image. It hid the poster only when expo-video reported the first frame. expo-video 57.0.5's web `VideoView` attaches its `loadstart` listener in an effect, and WebKit fires `loadstart` before that listener exists, so the first-frame event never arrives. On web, a resolved `play()` on the `<video>` element now also counts as the first frame. A rejected `play()` still keeps the poster. Found in end-to-end checks on October 11, 2026, in headless Playwright WebKit 26.6, desktop Safari 27.0.1 through `safaridriver`, and Mobile Safari 27.0 on an iOS 27 Simulator. The fix was checked the same day in those three and in headless Chrome 154: the poster hides once playback starts and frames advance and loop. Native iOS and Android were unaffected.
- `@assetlib/sdk-core` changes only its version and README. `@assetlib/cli` 0.3.1 and `@assetlib/audit` 0.2.1 are unchanged.

## 0.6.0-preview.1 — October 11, 2026

- Short looping video, following the Assetlib looping video contract. `@assetlib/cli` stays at 0.3.1, unchanged.
- `@assetlib/sdk-core`: the optional signed `videoSchemaVersion: 1` enables a `video` descriptor on base placements (`mp4`, `h264-loop-v1`, `video/mp4`, 1–4,194,304 bytes, even 16–1280 dimensions of at most 921,600 pixels at the placement's exact aspect ratio, 1,000–10,000 ms, 1–30 fps, same-origin `/assets/{assetId}/videos/{sha256}` URL). Any other `videoSchemaVersion`, `video` without the marker, `video` with `animation`, or `video` on a state member, variant cell or catalog page image rejects the release. New `client.resolveVideo(ref, { cachePolicy, signal })` downloads only for the current release, checks length, SHA-256 and a bounded MP4 header (`ftyp` first, `moov` before `mdat`, not fragmented, one `avc1` track at the signed size), caches through the storage adapter as `video/mp4`, and falls back to verified cached clips from older retained releases, then `source: 'poster'`. Ordinary `resolve` never downloads a clip. New client option `videoTimeoutMs` (default 30,000, 20–30,000), `SDK_LIMITS.videoBytes` (4,194,304), `StorageMime` `'video/mp4'`, and the optional storage method `getAssetFileUri`, with which `resolveVideo` returns a file `uri` instead of bytes and needs the `disk` policy. The shared contract corpus adds 27 manifest cases, 2 video resolution cases and 2 video byte-failure cases.
- `@assetlib/sdk-expo`: new entry point `@assetlib/sdk-expo/video` with `AssetlibVideo`: the `AssetlibImage` poster with the clip played muted and looping by `expo-video` (`nativeControls={false}`), only under allowed motion, while the app is active and while it holds one of two app-wide playback slots; any failure or a rejected web `play()` shows the poster. `expo-video` is an optional peer dependency (`>=57 <58`); the main entry does not import it. On iOS and Android the adapter caches clips as `<sha256>.mp4` (at most 4 MiB, same budget) and exposes their `file://` URI; `memory` and `none` give the poster there. On web, clip bytes become a Blob URL that is revoked on unmount. `createExpoAssetClient` accepts `videoTimeoutMs`.
- Limits: covered by Node unit tests with a simulated filesystem, IndexedDB and player only. Nothing has run on a device, simulator, emulator or browser, and `expo-video` does not document plain `file://` sources. Off-screen pausing is left to the app through the `paused` prop.

## @assetlib/audit 0.2.0 — October 10, 2026

- Only the audit is released, on npm. The SDKs and the CLI are unchanged from 0.5.2-preview.1. 0.2.0 also carries the `Vendor` skip listed under 0.5.0-preview.1, which npm's 0.1.0 does not have. The audit tarball attached to the v0.5.0-preview.1 GitHub release is labeled 0.1.0 but was packed from that later source, so it differs from npm's 0.1.0.

- `@assetlib/audit`: opt-in change history. `--history` (or `history: true`) runs local, read-only `git log` and counts first-parent changes that added, modified, or deleted an in-scope PNG, JPEG, WebP, SVG, asset-catalog PDF, or Lottie file, with every commit's date checked against a window ending at the checked-out commit's date (`--history-days`, default 365). Density and dark-mode copies of one image count once, and images are sorted by path conventions into artwork, icons and logos, and app icons with launch and store art. The report gains a `history` object (per kind: changes, image-only changes, distinct images, file changes, the largest change, changes by month; file changes by format; the 20 most changed artwork images) and `history.changes`/`lastChanged` on each inventoried asset. It reads commit times, changed paths, and submodule paths only, never messages, authors, hashes, or file contents. Git is found through absolute `PATH` entries outside the audited checkout and outside any `node_modules`; every call passes `--no-lazy-fetch`, so history needs git 2.44 or later and never fetches in a partial clone; inherited `GIT_*` variables are ignored; and signature checks, pagers, external diffs, and fsmonitor are off so repository configuration cannot run programs. A missing repository, a shallow clone whose history ends inside the window, a submodule in scope, or a history limit reports partial coverage (exit 2); history that could not be measured reports `null` counts. A shallow clone's cut-off commit is not counted, the commit limit counts only changes under the audit root, and the text report escapes control characters in file names.

## 0.5.2-preview.1 — October 10, 2026

- `@assetlib/cli` 0.3.0, unchanged from 0.5.1-preview.1 and attached to this release again. `@assetlib/sdk-core` changes only its version and README.

- `@assetlib/sdk-expo`: on iOS and Android, `client.resolveAnimation(ref)` under the default `disk` cache policy always returned `source: 'poster'`, so verified Lottie animations never reached the app's player. The native storage adapter accepted only PNG and WebP, so caching the verified JSON threw after a successful download, and it never looked for a cached animation. It now stores `application/json` as `<sha256>.json` in the same namespaced cache directory and reads it back. Each JSON entry is capped at 512 KiB (`LOTTIE_LIMITS.bytes`) and counts toward the same 50 MiB / 100 entry eviction budget as images. Other MIME types are still rejected, and raster storage, `.webp` compatibility and legacy namespace migration are unchanged. The core still rehashes and revalidates cached JSON on every read. The `memory` and `none` policies and Expo web were not affected.
- Limits: the SDK includes no Lottie player; the app supplies one. A cache write that fails after a verified download still returns the poster, just as a failed image cache write returns the bundled image. Native SVG and PDF delivery are still not implemented. The fix is covered by Node unit tests that run the real adapter source against a simulated Expo filesystem; it has not been run on an iOS or Android device or simulator.

## 0.5.1-preview.1 — October 10, 2026

- `@assetlib/cli` 0.3.0. `@assetlib/sdk-core` and `@assetlib/sdk-expo` change only their version.

- `@assetlib/cli`: `assetlib init` sets up an Expo app that has no catalog yet. It adopts bundled images as `adopt` does but starts from no catalog and creates it, copies a checked public configuration to `assetlib.public.json`, and writes a GitHub Actions workflow that runs `assetlib sync` from the installed package with the token from a repository secret. It is a dry run unless `--apply`, refuses an existing catalog, writes nothing when no image can be adopted (exit 3), and never calls Git or the network. `--image` limits it to chosen images. The workflow gives the token to the sync step only: actions are pinned to commits, checkout keeps no credentials, dependency install scripts are off, values reach scripts as environment variables, literals are validated and single-quoted, and a non-HTTPS console is never written into CI. `init` never writes through a symlink. Internally, the adopt planner can now start from a missing catalog and be limited to chosen images; the `adopt` command's behavior and output are unchanged.

## 0.5.0-preview.1 — October 10, 2026

- `@assetlib/cli` 0.2.0.

- Tintable icons, following the Assetlib tintable icon contract. A catalog placement may declare `"rendering": "template"` (or `original`, the default). Both codegen copies add `rendering: 'template'` to the generated reference only for template placements and reject any other value; catalogs without the field generate byte-identical output, and `assetlib sync` registers the field with the catalog.
- `@assetlib/sdk-core`: signed descriptors (placements, state members, variant cells and catalog page images) may carry `rendering`. A malformed value (null, a non-string, or anything not matching `^[a-z][a-z0-9-]{0,31}$`) rejects the release. A reference's rendering must equal the selected descriptor's (absent means `original`); a mismatch or a well-formed unknown value skips that descriptor like an incompatible size, with no cache read or download, and resolution continues with older retained cache and then the bundled fallback (`fallbackReason: 'missing'`). `AssetRef` gains `rendering?: 'template'` and `ResolvedAsset` gains `rendering`. The shared contract corpus adds 15 manifest cases and 10 rendering cases.
- `@assetlib/sdk-expo`: TypeScript requires `tintColor` on `AssetlibImage` and `AssetlibStateImage` when `asset` is a template reference, and a missing `tintColor` logs one development warning per placement. Template references without `pixelWidth` and `pixelHeight` request logical size × `PixelRatio.get()`, rounded up.
- Template descriptors come from a console that runs the tintable icon release. Older SDK versions do not check `rendering`, and older codegen drops it.
- `@assetlib/cli`: `assetlib sync --references` now finds Swift call sites. The Swift SDK's generated accessors lower-camel the group and add an artwork method, so `artwork.travel.coast` and `artwork.travel.coastArtwork(...)` now count as references to the `["Travel", "coast"]` symbol. These Swift forms apply only to two-segment symbols, and a form that another placement can also produce (for example with a `["Travel", "coastArtwork"]` or `["travel", "coast"]` symbol in the same catalog) is not credited to either placement. `AppAssets`, `AssetCatalog` and `artwork` matching of the exact symbol is unchanged, and longer names such as `artwork.travel.coastline` still do not match.
- `@assetlib/audit` and the `@assetlib/cli` reference scan now skip `Vendor` directories, the common iOS spelling. The ignore list, and the audit's reported `scope.ignoredDirectories`, now include `Vendor`. Names still match exactly, so first-party folders such as `Coverage` or `Target` are scanned.

## 0.4.1-preview.1 — October 9, 2026

- `@assetlib/cli` 0.1.1: the README now installs the CLI from the release tarball instead of npm, where it is not published. No code change from 0.1.0.
- Public configuration now accepts raw JSON strings and enforces a 4096-byte UTF-8 limit. Object inputs use their JSON serialization. Unknown fields and JSON whitespace count toward the limit.
- Configurations with duplicate PEM pins or more than 16 pins are now rejected. Each pin must be an Ed25519 SPKI PEM of at most 256 UTF-8 bytes.
- Near-limit configurations remain reusable by a client: derived IDs are omitted when adding them would exceed 4096 bytes. Supplied IDs and every trusted pin are preserved.
- The shared contract checks explicit nulls, invalid or mismatched IDs, and `keyId` without an explicit single pin. When both pin forms are supplied, the single pin must belong to the set; ordered `keyIds` must match every pin. Any trusted member may sign a release, including a member other than the single pin.
- The JavaScript tests now run every generated shared config case as both a JSON string and an object, including exact byte boundaries and signatures from a second trusted key and an untrusted key.
