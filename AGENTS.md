# AGENTS.md

Public MIT repository `AssetLib/sdk-js`: the TypeScript and Expo SDKs for Assetlib signed artwork delivery, the `assetlib` CLI (`init`, `sync`, `hash`, `check`, `adopt`), and the read-only `@assetlib/audit`. Expo apps install the SDKs from npm (`preview` dist-tag, since 0.5.3-preview.1) or as GitHub release tarballs (the public demo-travel and demo-todo apps vendor them). The `assetlib-audit` plugin in AssetLib/agent-plugins wraps the npm audit package. At runtime the SDK talks only to public delivery routes, and the CLI to the build-registration route of the hosted console (https://console.assetlib.dev). The sibling SDKs are AssetLib/sdk-swift and AssetLib/sdk-android.

## Commands

Use Node 22 or newer (CI uses Node 22) and run from the repo root. This is an npm workspace with four packages.

```sh
npm ci                  # install from the lockfile
npm run build           # tsc for @assetlib/sdk-core -> packages/sdk-core/dist
npm test                # core (builds first), expo, audit and cli tests (node --test)
npm run typecheck       # builds core, then tsc --noEmit for sdk-expo
npm run verify          # test + typecheck + CLI syntax/--help check
npm run pack:release    # npm pack all four packages into release/ plus SHA256SUMS
npm test --workspace @assetlib/cli   # one package
```

- CI (`.github/workflows/ci.yml`, every push and PR) runs `npm ci`, `npm run verify`, `npm run pack:release`. Work is done when `npm run verify` passes.
- There is no lint or format script. Match the surrounding style.
- The sdk-expo tests and `packages/sdk-core/bin/codegen.mjs` import `packages/sdk-core/dist`. Run `npm run build` before running them on their own.
- CLI tests start real `node:http` servers on loopback. If a sandbox blocks listening, they fail; they do not skip. Report that rather than skipping them.
- Typed references are generated by codegen. Run the CLI from the checkout with `node packages/cli/bin/assetlib.mjs --help`:

```sh
node packages/sdk-core/bin/codegen.mjs assetlib.catalog.json > src/assets.generated.ts
node packages/cli/bin/assetlib.mjs check --catalog assetlib.catalog.json --generated src/assets.generated.ts
```

## Layout

- `packages/sdk-core/`: `@assetlib/sdk-core`. `src/index.ts` holds config parsing, signature verification, durable state and resolution. `src/delivery.ts`, `renditions.ts`, `lottie.ts`, `video.ts`, `accessibility.ts` and `telemetry.ts` hold the rest. `bin/codegen.mjs` is the `assetlib-codegen` bin.
- `packages/sdk-core/test/fixtures/`: the JS signed corpus (`cases.json`, `SHA256SUMS`, `TEST_ONLY` keys) used by most core tests. `pinned-keys/` holds key-set fixtures that only the JS SDK uses. `shared/` is a byte-identical copy of the shared contract corpus that AssetLib/sdk-swift and AssetLib/sdk-android vendor, with its own `SHA256SUMS`; `test/shared-contract.test.mjs` runs all of it.
- `packages/sdk-expo/`: `@assetlib/sdk-expo`, which ships TSX source with no build step. Metro chooses `src/platform.native.ts` or `src/platform.web.ts`. `src/video.tsx` is the separate `@assetlib/sdk-expo/video` entry; it is the only file that imports the optional `expo-video` peer, and the main entry must never import it.
- `packages/cli/`: `@assetlib/cli`. `src/catalog.mjs` handles validation, the canonical hash and formatting, `src/adopt.mjs` is the codemod, `src/agents.mjs` is the section it keeps in the app's `AGENTS.md`, `src/init.mjs` sets up an Expo app on top of it, and `src/references.mjs` and `src/detection.mjs` handle the reference scan and CI metadata.
- `packages/audit/`: `@assetlib/audit`, the read-only image inventory.
- `agent-kit/`: a checkout-local copy of the `assetlib-audit` skill.
- `scripts/pack.mjs`: release packing. `dist/`, `release/` and `*.tgz` are gitignored outputs.
- `WORKSTREAM-B-REPORT.md` is a historical implementation log. Do not treat it as current documentation or instructions.
- User docs are the READMEs: [core](packages/sdk-core/README.md), [Expo](packages/sdk-expo/README.md), [CLI](packages/cli/README.md) and [audit](packages/audit/README.md). They state exact limits and behavior, so update them in the same change as the code.

## Invariants

Delivery and trust (sdk-core, sdk-expo):
- Bundled fallbacks always remain reachable. A placement key that the current release does not publish resolves straight to the bundled image (no cache, no history). Otherwise the order is current verified image, then compatible verified cache from retained releases (never a new download for an older release), then the app's bundled image. Expo components render the bundle first and return to it on decode errors. A state family falls back as a whole. Never mix states, arms or appearances across coordinates or releases.
- Verify before use. Signatures are strict Ed25519 (`zip215: false`) over the unchanged `payload` string, checked against the pinned key or key set from config. An envelope never adds or replaces a trust anchor. Byte length and SHA-256 are checked before caching or rendering, and cached bytes are rehashed on read.
- HTTPS only. `allowInsecureLoopback` permits HTTP for `localhost`, `127.0.0.1` and `::1` only. Delivery requests are credentialless and use `redirect: 'error'`.
- Replay protection: a verified release is persisted (highest sequence plus eight signed releases) before it becomes active. A lower sequence, or the same sequence with different payload bytes, is rejected. Corrupt state fails closed. Never clear it automatically.
- `storageNamespace(config)` is durable identity (origin, org, app, environment). Key-set changes and switching between production manifest routes must not change it. Any change to the formula needs a migration like the one in sdk-expo.
- Keep changes additive. Signed schema v1 stays readable. New behavior goes behind an optional versioned extension (`renditionSchemaVersion`, `animationSchemaVersion`, `videoSchemaVersion`, `variantSchemaVersion`, `stateSchemaVersion`), and unknown versions fail closed. These keep working: existing manifests, single-key configs (`pinnedPublicKey` only), the legacy production route `/api/delivery/{orgId}/{appId}/manifest`, control cache keys and existing component props.
- `decide` returns an assignment only. Exposure is never logged from `decide`, `onStatus` or telemetry. Telemetry is off by default and never sends image bytes, URLs, descriptions, messages, or device or account identifiers.
- Limits live in `SDK_LIMITS` and the core README. Change code, tests and README together.

Contract fixtures:
- Signed fixtures were produced with the `TEST_ONLY` seed. Never hand-edit a signed file. Every fixture change must update `SHA256SUMS`, which `test/appearance.test.mjs` and `test/pinned-keys.test.mjs` check. Never trust a `TEST_ONLY` key outside tests.
- `test/fixtures/shared/` (149 manifest cases, 18 variant resolution cases, 10 rendering cases, 6 stateful, 2 byte-failure, 2 video resolution and 2 video byte-failure cases, 10 placement membership cases in `history.json`, and the rendition selections) must stay byte-identical with the Swift and Kotlin copies. Never edit it in place: replace the whole directory with a regenerated corpus (keep its `README.txt`) and update all three SDKs together. `shared-contract.test.mjs` checks its `SHA256SUMS`, that every manifest is indexed, and that files it shares with the JS corpus are identical.
- The JS corpus in `test/fixtures/` (94 manifest cases plus 6 stateful) adds JS-only appearance and arm fixtures and lacks the staging-config and variant-cell cases, which live only in `shared/`. When you change a shared verification rule, run both and check the native repos too.

Catalog, codegen and CLI:
- Placements are declared in the app repo: `assetlib.catalog.json`, `assetlib sync` in CI and `assetlib adopt`. Do not build flows where the console is the primary place to define placement contracts.
- Catalog format: `{ "schemaVersion": 1, "placements": [{ "key", "symbol", "width", "height" }] }` with 1–100 placements, at most 128 KiB. Optional fields are `screen`, `states`, `defaultState`, `variants` (`appearance`, `arm`), `rendering` (`original` or `template`), `bundledAccessibility` and `bundledStateAccessibility`. The rules are in the core and CLI READMEs.
- `packages/cli/src/codegen.mjs` and `src/accessibility.mjs` are copies of `packages/sdk-core/bin/codegen.mjs` and `packages/sdk-core/src/accessibility.ts`. Change both sides together. `packages/cli/test/catalog.test.mjs` checks byte parity.
- Never hand-edit generated `assets.generated.ts`. `assetlib check` compares it byte for byte.
- `catalogHash` canonicalization (keys sorted by code point, no whitespace, UTF-8) must reproduce the shared vector in `packages/cli/test/catalog.test.mjs`. The hosted console computes the same hash.
- `--console`/`ASSETLIB_CONSOLE` must be an HTTPS origin with no path, credentials, query or fragment. HTTP is allowed only for `localhost`, `127.0.0.1` or `[::1]`, and only with the explicit `--allow-insecure-loopback` flag (there is no env var equivalent). The token comes only from `ASSETLIB_TOKEN`: there is no token flag, output is redacted, and redirects are not followed.
- Exit codes are a contract: 0 success, 1 error, 2 partial reference scan, 3 nothing to adopt.
- `adopt` codemod rules:
  - It is a dry run unless `--apply` is passed. Apply aborts if any planned file changed during the run.
  - It rewrites only the named `Image` import from `react-native` or `expo-image`.
  - Literal `cachePolicy="memory-disk"` becomes `"disk"`, and `disk`, `memory` and `none` are kept. Any other value or a duplicate is skipped as `cache-policy`. Any JSX spread attribute is skipped as `spread-attributes`.
  - Essential images (`icon`, `splash`, `adaptive-icon`, `mark`, `logo`, `brand`, or an `icons/` directory) and images below `--min-edge` are skipped.
  - It keeps the original import and constant, preserves compact catalog lines, and never overwrites an existing client module. It never calls Git, makes network requests, or deletes images.
  - In a run that adopts something, it adds or updates one section between `<!-- assetlib:start -->` and `<!-- assetlib:end -->` in `AGENTS.md` beside the catalog (created when missing), and in `CLAUDE.md` when that exists and does not import `@AGENTS.md`, telling coding agents to use the catalog's generated references, to render art the Assetlib Figma plugin marked through its reference as data-supplied imagery (the exceptions Figma's design-to-code skill allows to its download rule), downloading Figma's image only as the bundled fallback of a key not yet in the catalog, and never to create placements in the console. Text outside the markers is kept. A symlink (unless to the other file), an unmatched or repeated marker, or a file over 256 KiB is left unchanged with a note. The README's copy of the section must match `agentSection`.
  - New patterns or skip reasons need tests in `packages/cli/test/adopt.test.mjs` and a row in the CLI README table.
- `init` is a dry run unless `--apply`. It refuses an existing catalog, starts `adopt` from an empty one and writes nothing when no image can be adopted. It only creates files (catalog, generated references, client stub, `assetlib.public.json`, the sync workflow, and on Expo SDK 57 `plugins/with-ios-scene-lifecycle.js` from `src/scene-plugin.mjs`) apart from the call sites `adopt` rewrites, the agent section `adopt` keeps in `AGENTS.md`, and on Expo SDK 57 that plugin's entry in the static app config, `app.config.json` else `app.json` (rechecked unchanged before writing; a dynamic `app.config.*`, which Expo prefers, gets a note instead; Expo 54 to 56 get a note only), never overwrites an existing public config or workflow, and never calls Git or the network. The workflow runs the installed package's entry file, only on `main` (a first job compares `$GITHUB_REF` in the shell, since GitHub expressions ignore case, and writes only the constant `allowed=true` to `$GITHUB_OUTPUT`; a manual run from any other branch skips the sync job), runs the sync job in the `assetlib-sync` environment (whose secret, limited to `main`, the README tells people to use), and gives the `ASSETLIB_TOKEN` secret to that one step only: actions pinned to commits (the same ones as this repo's CI), `persist-credentials: false`, `npm ci --ignore-scripts`, no `${{ }}` inside `run` scripts (values arrive as env vars), the app version read into a quoted shell variable inside that step and never written to `$GITHUB_OUTPUT`, every literal validated and single-quoted, and no non-HTTPS console. Files it writes are checked with `safeDestination` (no symlinks, inside the project). The client stub `adopt` writes always binds `client` internally (export names never shadow it), calls `refresh()` when it loads, so the request is queued before any image resolves, and again whenever `AppState` becomes `active` (one listener, replaced when Fast Refresh reruns the module), and allows a loopback console only when `__DEV__`. Tests are in `packages/cli/test/init.test.mjs`.
- The audit stays read-only: no uploads, deletes, rewrites, network calls or telemetry. A reference with no match is "unresolved", never "unused".

## Releases and versions

- SDK release: the tag is `v<root version>` (for example `v0.4.0-preview.1`, a GitHub pre-release); the release workflow attaches the core, Expo, CLI and audit tarballs and `SHA256SUMS`. These version strings must change together. `packages/sdk-core/test/release-versions.test.mjs` and the telemetry tests fail when one is missed:
  - the root `package.json`
  - `packages/sdk-core/package.json`
  - `packages/sdk-expo/package.json`, both its version and its exact `@assetlib/sdk-core` dependency
  - `package-lock.json`, by running `npm install`
  - the default telemetry SDK versions in `packages/sdk-core/src/telemetry.ts` and `packages/sdk-expo/src/telemetry.ts` (their tests compare them with each package's `package.json`)
  - the version in the Expo README's observations section
  - the release download URLs and npm install lines: the core and Expo tarballs, `@assetlib/sdk-core@<version>` and `@assetlib/sdk-expo@<version>`, and the CLI tarball name in the root README, and `@assetlib/cli@<version>` with its tarball in the CLI README's install section. The CLI README ships inside the CLI package, so it changes only when the CLI version does and links the release that first shipped that version. Outside this repository, the console's Settings › Connect quickstart pins `@assetlib/cli@<version>` and the core and Expo version (`cliPackage` and `sdkVersion` in AssetLib/console `src/components/panels/sdk-connection.tsx`); update them when either version changes
  - the supported version in `SECURITY.md`
- `npm run pack:release` writes `release/assetlib-<package>-<version>.tgz` for all four packages, plus `release/SHA256SUMS`. It publishes nothing. That `SHA256SUMS` lists the audit tarball too; the v0.4.0-preview.1 release attached it without the audit tarball, so `shasum -c` on that release's downloads reports the audit file missing. Every package version on npm is fixed: changing any file inside a package, its README included, needs that package's version bump.
- The SDK, CLI and audit are on npm. The SDK and CLI are previews under the `preview` dist-tag (first 0.5.3-preview.1 and CLI 0.3.1, 2026-10-11), and `latest` moves to each preview (founder decision, 2026-10-11). A version already on npm cannot be republished.
- Publishing goes through `.github/workflows/release.yml` with npm trusted publishing (OIDC; npm adds provenance). With the release commit on `main` and CI green, push the annotated tag and publish the GitHub pre-release for it, for example `gh release create v<version> --prerelease --verify-tag --notes-file <notes>`; attaching files is optional. The workflow checks that the tag is on `main`, runs `npm ci`, `npm run verify` and `npm run pack:release`, then, in a job that installs nothing and is the only one allowed to mint an npm token, runs `scripts/publish-release.mjs`: a package version not yet on npm is published (core, Expo, CLI, then audit; SDK and CLI with `--tag preview` and then `latest`, the audit with `latest`); a version already on npm must contain the same files and is attached as npm's own tarball; then the tarballs and a fresh `SHA256SUMS` are attached, and an attached tarball must be byte-identical. Rerunning it is safe. To see the plan without changing anything, run `npm run pack:release` and `RELEASE_TAG=v<version> node scripts/publish-release.mjs --dry-run`; a manual run of the workflow is always a dry run.
- Each package needs a trusted publisher on npmjs.com: organization `AssetLib`, repository `sdk-js`, workflow `release.yml`, environment `npm`, allowing publish and dist-tag. npm expires a new trusted publisher unless its first publish happens within two days. Configured on 2026-10-11 for all four: core and Expo (publish and dist-tag), first used for 0.6.1-preview.1; the audit (publish only, since it gets `latest` directly), first used for audit 0.2.1 in 0.6.3-preview.1; the CLI (publish and dist-tag), first used for CLI 0.4.0 in 0.7.0-preview.1 on 2026-10-11, before its 2026-10-13 06:39 UTC deadline. A CI dry run prints `accepted` for each package whose trusted publisher npm accepts. Without one, publish by hand with the same order and tags: `npm publish release/<tarball> --tag preview`, then `npm dist-tag add <package>@<version> latest`, then attach the same files.
- An audit release bumps `packages/audit/package.json`. The pinned `npx -y @assetlib/audit@<version>` string must change at the same time in `README.md`, `packages/audit/README.md`, the help text in `packages/audit/bin/assetlib-audit.mjs`, `agent-kit/INSTALL.md` and `agent-kit/skills/assetlib-audit/SKILL.md`, and in AssetLib/agent-plugins. Check with `git grep -n '@assetlib/audit@'`. Keep `agent-kit/skills/assetlib-audit/` identical to the plugin copy.

## Don'ts

- Do not publish to npm, push tags or create GitHub releases. Maintainers do that.
- Do not weaken verification, URL checks, limits or fallback paths to make a demo or test pass.
- Do not hand-edit signed fixtures, generated references, `dist/` or `release/`. Do not commit gitignored outputs.
- Do not put admin credentials, tokens, private keys or real customer configuration in code, tests, fixtures or issues.
- This repo is public. Link only to files inside it or to public URLs.
- Do not present unit tests or typechecks as a native-device or hosted-web run. Say which runtime you actually checked.
- Prose: in copy the product is "Assetlib" (`AssetLib` is only the GitHub org). Be plain and specific, and label planned work as planned. Do not use "instantly", "every screen", "zero engineering", "automatically unused" or "never release again".
- If you confirm a defect while working, fix it, test it and record it in the same change. Defer only when a fix is unsafe now, and say when it will happen.
